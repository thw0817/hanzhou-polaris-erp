## 2. 产品目标

这是一个店群管理软件，不是演示后台，也不是单一店铺看板。目标用户是运营团队，核心工作是：

- 管理多个授权 SHEIN 店铺，保留每个店铺的备注名称；
- 按成员权限隔离店铺、商品、任务和模板；
- 读取真实经营数据，查看销量、库存、商品状态和经营预警；
- 读取真实合规要求，按 SKC 定位不合格原因；
- 在单个 SKC 页面修复合规资料，引用合规模板、上传实拍图和证书，保存本地草稿；
- 运行服务端 dry-run 预检，明确展示阻断项；
- 本地验证闭环通过后，再评估云端部署和正式写入能力。

当前优先级：

1. 本地真实链路稳定可打开；
2. 经营数据真实同步；
3. 合规数据真实同步；
4. 单 SKC 合规详情不白屏且能读到真实规则；
5. 单 SKC 引用模板、上传资料、保存草稿、dry-run 预检；

## 6. 下一阶段必须实现的闭环

### 6.1 本地 V2 只读规则刷新

在 `server/v2-local-real-server.js` 增加本地适配路由，建议契约：

```text
POST /v1/web/stores/:storeId/compliance-workspace/:skc/rules/refresh
```

行为：

1. 从本地合规缓存找到该 SKC 的真实 row；找不到时返回明确的“请先同步合规数据”；
2. 通过 `legacyRequest` 调用旧代理的 `/compliance/rules`；
3. 把官方 bundle 投影为当前 V2 的：
   - `ComplianceRequirementRecord[]`；
   - `ComplianceRuleSnapshot[]`；
   - `ComplianceEditorModel`；
4. 规则快照必须包含 `fetchedAt`、`expiresAt`、`fresh`、traceId/source coverage；
5. 只读接口失败必须保留上游 code/message/traceId，不伪造快照；
6. 该接口只能刷新读取和本地缓存，不能调用 SHEIN 合规写接口。

详情页增加“刷新合规数据”按钮，成功后重新读取详情。按钮状态应明确显示读取中、成功、失败；不要让用户只能点“重新读取”却永远得到空状态。

### 6.2 商品属性与 1630/1631 判定

详情接口不能把缺失属性快照当作正常完成状态。实现顺序：

1. 通过旧代理读取 `/api/shein/stores/:id/products/identify`，得到真实 SPU 详情；
2. 读取或刷新 `/api/shein/stores/:id/template/attributes`，参数使用真实 `productTypeId`；
3. 复用 `src-v2/lib/attribute-template-contract.js` 的 `buildAttributeFields` 语义，过滤销售属性、SKU/包装维度属性；
4. 建立 truthful `attributeSnapshot`：字段总数、已赋值字段数、字段 ID、值 ID、原始值、来源和获取时间；
5. 只根据官方属性值判定 1630/1631。没有足够官方属性时显示阻断原因，例如“缺少官方商品属性”或“无法判定”，不能默认通过；
6. 先实现只读展示和证据解释。商品属性修改接口仍然关闭，除非后续单独确认官方写接口、权限和审计方案。

### 6.3 草稿保存

实现前端已使用的契约：

```text
GET /v1/web/stores/:storeId/compliance/drafts/:skc
PUT /v1/web/stores/:storeId/compliance/drafts/:skc
```

保存内容：

- `requirementSnapshot`：当前有效规则 payload；
- `inputs.certificates`：证书池引用或本地资料引用；
- `inputs.agencies`：代理公司选择；
- `inputs.warnings`：警示语选择；
- `inputs.photos`：商品实拍、包装实拍媒体引用；
- `preflight`：本地保存的 dry-run 摘要；
- `status`：至少支持 `draft`，不能伪造 `submitted`。

本地草稿建议持久化到 `.data` 下的本地文件，key 至少包含 `storeId + skc`，并用 `expectedUpdatedAt` 做并发保护。若首轮选择内存实现，必须明确标为临时方案并补持久化测试，不能让用户误以为重启后草稿仍在。

### 6.4 本地合规证据上传

前端 `src-v2/lib/api.ts` 已按云端媒体契约调用：

```text
POST /v1/web/stores/:storeId/media/upload-ticket
PUT  ticket.upload.url
POST /v1/web/stores/:storeId/media/:assetId/complete
```

本地适配器应实现：

- 文件名、MIME、大小校验；
- 本地临时/正式媒体目录，权限 `0700/0600`；
- upload-ticket 返回本地 PUT URL；
- complete 校验 SHA-256、大小和上传状态；
- 返回现有 `MediaAsset` 契约；
- 草稿只保存 `media:<id>` 引用，不把 base64 或文件字节塞进 JSON；
- 不把本地媒体上传到云端或 SHEIN；
- 证书 PDF、PNG、JPG、JPEG 与实拍图的大小限制分开定义，沿用现有项目边界。

### 6.5 合规模板引用

单个 SKC 页面应允许用户：

1. 读取当前店铺的合规模板列表；
2. 选择“引用模板”；
3. 将模板中的合规默认资料映射到当前 SKC 草稿；
4. 对不可复用项保留为空并提示原因；
5. 用户可以继续替换当前 SKC 的商品实拍图；
6. 引用模板后必须以当前 SKC 的新规则快照重新校验，不能只看模板保存时的中文名称；
7. 1630/1631 报告必须按项目既有规则判断是否需要当前 SKC 单独上传，不能错误复用不允许复用的证书。

模板只是默认输入来源，不等于向 SHEIN 提交。保存后仍必须运行本地服务端 dry-run。

## 8. 必须采用的修复规则

每一个新 bug 都执行以下循环：

1. 记录用户操作、URL、当前店铺、SKC、接口和浏览器错误。
2. 判断属于 UI、V2 契约、本地代理、SHEIN 适配、缓存、任务、云端、数据库还是环境。
3. 找到唯一 owner module，说明允许修改的文件。
4. 先写最窄回归测试，让测试真实复现问题。
5. 做最小修改，不顺手重构相邻模块。
6. 先跑目标测试，再跑受影响模块测试。
7. V2 受影响时跑 `npm run build:v2`。
8. 后端影响扩大时跑 `node --test server/*.test.js`。
9. 用本地浏览器复现原操作，检查页面、网络响应和控制台错误。
10. 审查 diff：是否越过模块边界、是否制造数据、是否泄漏密钥、是否打开写接口。
11. 在本文件追加一条记录，写清根因、修改、测试和仍未完成事项。

成功标准不是“页面能显示”，而是：

- 真实数据来源明确；
- 空数据与失败可区分；
- A 的修复不改变 B 的数据语义；
- 刷新、重试和并发有明确状态；
- 可通过自动化测试和本地浏览器验收；
- 云端发布门禁保持关闭，直到本地闭环完整通过。
