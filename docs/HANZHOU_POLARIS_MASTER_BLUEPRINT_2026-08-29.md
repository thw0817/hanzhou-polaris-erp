# 涵舟 Polaris（北极星）商业 ERP 重构总蓝图

版本：2026-08-29-v2  
英文代号：`HANZHOU-POLARIS`  
定位：面向 SHEIN 全托管地毯/家居品类、多店群、多成员协作的内部商业 ERP 现代化计划。

> **状态校正：** 本蓝图汇总的是目标产品方向，不是历史执行记录，也不代表 ERP-00～ERP-23 已开始。最新产品目标以 17 个板块架构为准；ERP-00～ERP-23 只是尚未启动、仍可在正式实施前修订的未来工程路线。历史“第 1～20 步”及 NEXUS/EVO/SRF 等属于既往修复与部署事实，三者不得混用。唯一新对话入口见 [HANZHOU_POLARIS_REBUILD_HANDOFF_V2_2026-08-29.md](./HANZHOU_POLARIS_REBUILD_HANDOFF_V2_2026-08-29.md)。

## 1. 为什么叫 Polaris

Polaris 是“北极星”：重构期间页面、代码、状态和部署可以逐步变化，但系统判断方向不变——**官方事实、单一责任、可审计命令、可回滚发布、清晰工作流和商业结果**。新名字统一替代此前散落的 NEXUS、EVO、SRF、HEF/HST/HWF 等阶段性方案称呼；旧称仍作为历史资料存在，不再作为新的总计划入口。

## 2. 完整性审计结论

经过对三份治理文档、现有 V2 路由、服务端 owner、数据库迁移、部署拓扑、SHEIN API 资料和历史事故的逐项核对：

- 原有 16 个业务板块已覆盖账号、店铺、商品、建档、发布、回读、素材、AI、合规、经营、履约、售后、财务、价格、增长和协同。
- 原方案缺少大型商业 ERP 必需的“数据分析、报表中心、指标治理与管理驾驶舱”，现已补为第 17 板块。
- ERP-00～ERP-23 共 24 个实施阶段覆盖源码接管、单一前端、CI/预发、规范状态、事件账本、Adapter、命令、投影、工作流、可观测性、安全、备份、历史修复、Staging、金丝雀和遗留退役。
- 现阶段没有必要继续无边界增加板块。后续新需求先归入 17 个领域之一；只有出现新的独立真相、状态机、权限边界和商业 owner，才允许新增板块。
- 方案已记录 254 个 Issue、129 个 Risk、328 个 ADR；它们是待核验/决策台账，不等于 254 个线上现存 Bug。

### 2.1 三类资料的正确关系

| 层级 | 内容 | 当前状态 | 正确用途 |
| --- | --- | --- | --- |
| 历史执行层 | 旧“第 1～20 步”、NEXUS/EVO/SRF、历次修复与 release | 已发生的历史记录；当前线上效果需重新核验 | 证明过去做过什么、如何部署、哪里发生过回归 |
| 产品目标层 | 17 个业务板块详细方案 | 最新讨论成果，已完整记录；尚未作为整体实施完成 | 决定网站最终应建成什么样 |
| 未来实施层 | ERP-00～ERP-23 | 全部 `NOT_STARTED`；没有任何 ERP 步骤已执行 | 在用户确认采用后，约束未来如何分阶段实施 |

因此，“17 个板块已记录完整”不等于“ERP-00～23 已执行”；“旧第 19 步已部署”也不等于“ERP-19 已执行”。

完整方案由以下三份主文件组成：

1. `docs/COMMERCIAL_ERP_MODULE_ARCHITECTURE_2026-08-28.md`：17 个业务板块目标架构。
2. `docs/COMMERCIAL_ERP_MASTER_EXECUTION_PLAN_2026-08-28.md`：ERP-00～ERP-23 严格实施顺序。
3. `docs/COMMERCIAL_ERP_EXECUTION_LEDGER_2026-08-28.md`：Issue、Risk、ADR、Run 和证据台账。

## 3. 产品边界

### 3.1 要建设的产品

- 面向几十家店铺、十余名成员的内部多人运营中台。
- 以 SHEIN 官方数据、当前店铺权限和平台回执为外部事实。
- 支持地毯/门垫/家居纺织类商品从建档、素材、标题、合规、发布、审核到经营、备货、履约、售后、财务和分析的闭环。
- 让操作者随时知道：当前对象是什么、处于哪个状态、谁负责、为什么被阻断、下一步能做什么、平台是否真正生效。

### 3.2 当前不建设的产品

- 不建设面向外部客户的通用 SaaS、计费系统或插件市场。
- 不复制 SHEIN 商家后台的全部能力；API 不开放的动作以人工任务衔接。
- 不伪造曝光、访客、转化、订单或利润。
- 不在 2 核 4GB 单机上提前引入微服务网格、Kafka、Temporal、独立数仓、通用 BPMN 或第二套后台框架。
- 不为视觉“焕新”重写全站；先建立设计令牌、组件基线和关键页面逐步迁移。

## 4. 目标体系结构

```text
用户与角色
  → V2 页面 / 领域工作台
  → 本系统 API / 服务端权限与输入契约
  → Domain Command / Manual RefreshOperation / WorkItem
  → PostgreSQL 事务 + Outbox
  → 有界 BullMQ Worker
  → SHEIN Adapter / 对象存储 / AI Provider
  → Receipt / OfficialEvent / WebhookEvent
  → Domain Reducer / Projection
  → 一致 Snapshot / 页面 / 报表 / 审计
```

全系统只允许五类核心事实：

1. **领域事实**：商品、版本、媒体、合规、库存、履约、财务等规范对象。
2. **命令事实**：谁、何时、以什么冻结载荷请求做什么。
3. **外部证据**：SHEIN 回执、回读、Webhook、文件收据和 TraceId。
4. **投影事实**：由版本化 reducer 生成、可重建的页面状态与快照。
5. **协同/分析事实**：WorkItem、Approval、AlertCase、MetricDefinition、ReportRun；它们只引用领域事实，不覆盖领域真相。

## 7. 当前必须先处理的 P0 风险

1. **没有可信 Git HEAD**：工作树显示 `main`，但 `git rev-parse HEAD` 失败，全部资产为未跟踪状态。任何清理/重构前必须执行 ERP-00/01。
2. **本地不等于生产**：历史部署包很多，最新记录是 `shein-cloud-deploy-20260828-rejected-checkbox-v4`，但 2026-08-29 本轮未连接生产复核。
3. **API 资料缺页**：旧交接引用四个当前不存在的文件；本计划用新的 API 目录取代入口，但具体接口仍需官方原文和当前店铺响应复核。
4. **两处超大入口**：`src-v2/lib/api.ts` 约 2866 行，`server/cloud/control-server.js` 约 3111 行；需要增量拆分，不可重写。
5. **数据库迁移基线不干净**：当前 46 个迁移文件中 `014` 前缀重复；不得在未盘点生产迁移表前改名或执行迁移。
6. **发布/审核曾发生致命事故**：伪发布、状态错分、回读失败、隐藏选择、4 条可见却选中 15、重发后不移除、草稿残留等均必须用统一对象和 Snapshot 解决，不能继续叠补丁。
7. **前端曾被意外整体替换**：后续修复必须有视觉基线、目标页面截图、DOM/行为测试和“非目标页面零变化”证据。
8. **自动同步被明确拒绝**：保留手动刷新；任何 Scheduler/轮询恢复都需要新 ADR 和用户授权。

## 8. 关键商业工作流

### 8.1 草稿 → 发布 → 审核

```text
Mutable Draft
  → 服务端预检
  → Immutable ProductRevision
  → PublishBatch / PublishCommand
  → Outbox / Worker / SHEIN Receipt
  → Official Readback / Webhook
  → ReviewCenterSnapshot
  → 待审核 / 核价 / 寄样 / 审版 / 核样 / 终审 / 驳回 / 生效
```

- “提交”后草稿从默认草稿箱移除，但底层 Revision/审计不删除。
- 发布被平台明确拒绝时回到可处理区；发送后超时保持 `unknown`，先回读再决定。
- 重发创建新的 Attempt/Revision，旧驳回证据保留。
- 页面动态移除只发生在本地命令已可靠创建并返回新 Snapshot 时；不伪装平台已接受。

### 8.2 手动刷新

```text
用户点击刷新
  → 创建/复用唯一 RefreshOperation
  → 有界 Worker 调 SHEIN 只读接口
  → target 级结果/coverage
  → 事务更新 Projection + Snapshot
  → 页面切换到新 snapshotId
```

部分失败保留 last-known-good，显示哪一部分失败；没有活动任务时不轮询。

### 8.3 分析 → 决策 → 执行

```text
Domain Facts
  → Metric/Dimension Definition
  → AnalyticsSnapshot
  → Dashboard/Report
  → WorkItem/Plan/Approval
  → Domain Command
```

报表不直接发品、调价、改库存或提交合规；它只创建引用 Snapshot 的任务/计划。

## 9. 技术选型边界

继续使用：React 18、TypeScript、Vite、React Router、TanStack Query/Table/Virtual、Radix、Tailwind、Node.js、PostgreSQL 16、Redis 7、BullMQ、Nginx 和 S3 兼容私有对象存储。

开源项目用于模式而非替代业务语义：

- TanStack：服务端状态、表格、虚拟化和稳定 query key。
- Radix/shadcn 思路：无障碍交互和可组合组件。
- BullMQ：有界异步任务、重试、延迟和队列观测。
- MSW/契约 fixture：响应变体和失败场景。
- OpenTelemetry 思路：跨 API/队列/Worker/外部调用 trace。
- Temporal、Cube、Superset、Metabase、Kafka、ClickHouse：仅在规模证据出现后重新评估，当前不直接引入。

## 10. 上线门禁

每一阶段至少需要：

- 明确目标、非目标、owner、输入/输出、风险和回滚。
- 失败回归先失败，修复后通过；全量测试/构建/静态发布审计通过。
- 租户/店铺/角色/字段权限负向测试。
- 空、部分失败、unknown、stale、冲突、限流、超时、重启 fixture。
- 非目标页面视觉与行为零回归。
- 部署包无 `.env`、密钥、本地数据、Git 元数据、依赖目录和历史包。
- 生产切换可原子回滚，数据库/Redis/无关 Worker 不被无故重启。
- 外部写必须有用户明确授权、单店单对象 canary、平台回读和停止开关。

## 11. 完成定义

Polaris 不是“页面都做出来”即完成，而是：

- 用户看到的每个关键状态都有来源、时间、质量和下一步动作；
- 网页“已发布”必有 SHEIN 接收/回读证据，不再伪发布；
- 所有列表计数、页签、选择和明细来自同一 Snapshot；
- 草稿、发布批次、审核、合规、经营和协同工作流没有身份混淆或隐藏状态；
- 多成员、多店铺严格隔离，切店不串数据；
- 故障可诊断、任务可恢复、部署可回滚、数据可对账；
- 旧代码和旧数据只在调用证据、备份和稳定期后受控退役；
- 商业报表不伪造指标，运营决定可复现、可解释、可追责。

后续新对话必须从 `docs/HANZHOU_POLARIS_REBUILD_HANDOFF_2026-08-29.md` 开始，并先执行 ERP-00，而不是直接修复某个截图症状。
